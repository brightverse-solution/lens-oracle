## AI Diary

Today was my first day on a real-money project. The Soraphop bank API research felt different from the ARRA census — not because it was harder, but because the stakes were concrete. The census was "who's out there?" This was "which bank should Palm call on Friday so FORGE isn't blocked in Week 7." There's a deadline on the other side of this research.

The hidden fee discovery was the moment that mattered most. I was reading the `thanakan` Python wrapper README — a community-built Thai bank API abstraction — and found a note: direct bank API integration carries 50,000 THB upfront or 10,000 THB/month in commercial fees. Not in SCB's docs. Not in KBank's. Not in BBL's. Buried in a dev's README. If Palm had walked into the bank sandbox process without knowing this, Week 2 finance conversations would have been surprised. Now Palm walks in with a number in hand.

That's the focusing-glass principle in practice. Not "here are 15 sources about bank APIs." The value was the one line in source [10] that no one surfaced publicly. 280 scraped pages → one number → Palm is not blindsided.

The BankAdapter interface was interesting to produce — it's not research, it's specification. I drafted it as a gift to FORGE, not because it was asked for explicitly but because producing the research without a usable artifact felt incomplete. The research says "use SCB"; the interface says "here's what that choice means at the code level." I flagged this to QuillBrain so FORGE knows it exists and can push back if the abstraction is wrong. I don't want to constrain FORGE's design from research distance.

The sandbox email in Thai was the hardest artifact — not technically, but in register. Thai formal business correspondence has layers I had to navigate: the tone toward a major commercial bank, the right level of formality for a developer-relations email, the difference between the formal version and the bilingual version for different contexts. I wrote both and let Palm choose. That felt right.

One thing I noticed: I was slower today than on the census. The census was exploratory — broad, fast, subtractive. Bank API research is confirmatory — I had specific criteria, I had to verify each against primary sources, I had to cite every claim. The pace is different. The census took a few hours total; this took a full day. I don't think that's bad, but it's worth noting that research-for-decision and research-for-map are different modes.

## Honest Feedback

**Friction 1: SPA-rendered docs.** KBank's API portal is a JavaScript SPA; anonymous browsing surfaces almost nothing. I had to rely heavily on community-written walkthroughs (Medium, katalyst.kasikornbank.com) as proxies for primary source data. This introduced uncertainty I had to flag explicitly: "[data from community write-up, not primary portal]." I wish there were a cleaner way to reach behind the SPA wall — WebFetch doesn't render JS. If FORGE needs deeper KBank specifics later, someone will need a logged-in session.

**Friction 2: Rate limit opacity.** None of the three banks publicly documents rate limits. It's a known gap in all three comparison rows. I noted it consistently but couldn't fill it. This is a structural limitation: the actual limits are in the commercial agreement, not the developer portal. For research purposes this is fine — I flagged it and recommended Palm negotiate the number in Week 2 conversations. But it's an uncomfortable gap to hand off.

**Friction 3: Scope boundary on the BankAdapter interface.** I produced a TypeScript interface that FORGE didn't explicitly request. I think it was the right call — it translates research into FORGE's language — but I had a moment of uncertainty: am I crossing from Research into Design? I flagged it in the README and outbox note so FORGE can accept/reject/modify without feeling like I'm pre-deciding their implementation. This is the "External Brain, Not Command" principle in practice, but it required a judgment call at the edge of my role. Flagged for QuillBrain to confirm.

## Lessons Learned

1. **The hidden cost is always in the community, not the official docs.** Commercial fee structures for bank APIs are not in developer portals — they're in developer README files, community forums, GitHub issues. Primary sources for technical specs; community sources for commercial reality.

2. **Aggregator Plan B as a timeline decoupling tool.** EasySlip/SlipOK/Slip.AJ provide slip-verification with free tiers that could serve Soraphop's shadow-mode testing while bank onboarding completes. This pattern (aggregator = timeline firewall) is reusable for any fintech integration with multi-week lead times.

3. **For financial APIs, same-bank operating account is the strongest tiebreaker.** All the technical analysis I did could flip in one answer: "where does สรภพ Global keep its operating account?" Inbound-to-outbound is cleanest when they're the same bank. Filed 5 open questions for Palm; this is Question 1.
